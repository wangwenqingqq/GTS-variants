# N0：本轮机制边界（2026-10-04）

本轮执行 `480bc7d:PLAN_10K.md` 的稳定性验证。暂不提出新优化机制；保留 P7 的 O_BOUND 默认策略、O_FULL/O_MASK 控制及外部原生实现。下表是文献重叠审查，不是新颖性已成立的结论。

| 问题/机制 | 最近原始来源与重叠 | 本轮能检验的窄结论 | 最强替代解释/最低成本反证 |
|---|---|---|---|
| GPU 度量树、批量检索、更新 | [GTS](https://arxiv.org/abs/2404.00966) 已包含 pivot 树、批量查询及更新；原始 kNN 已有实际同 pivot 的复用 | P7 执行器在新 10K 输入上的完整输出与稳定性 | 改善来自原版低效实现；直接比较原生 Flat/IVF/CAGRA |
| 查询分组与共享数据 | [G-PICS](https://cse.usf.edu/~tuy/pub/SSDBM18.pdf) 已处理 GPU 并行空间查询与更新 | 既有 P4 度量树机制在指定高维范围条件下是否有净收益 | 普通批处理即可解释；保留共同输出管线的 SCAN 控制 |
| 树布局、访存与线程映射 | [Harmonia](https://www.ece.lsu.edu/lpeng/papers/ppopp-19.pdf) 已研究 GPU B+tree 的布局与查询聚合 | 地址、真实流量、执行工作各自的贡献 | 工作量或跨查询复用也变化；地址控制未成立时不叫纯合并访存贡献 |
| 分配、选择器、批次与流 | [Faiss 官方 GPU 文档](https://github.com/facebookresearch/faiss/wiki/Faiss-on-the-GPU) 已说明 scratch 复用、批量及流配置 | 实际 Host-ready 差距，特别是库自己的大批次 | Python 控制/选择器/默认批次限制；同时报告 bulk 与 matched |
| 高质量 GPU ANN | [CAGRA](https://arxiv.org/abs/2308.15136) 是原生 GPU 图搜索 | 99%、99.9% 与集合上的经验 100%，逐查询输出 | 高维近似与精确任务不同；不把平均 Recall 四舍五入当完整性 |
| GPU 更新可见性与驻留 | [MVGpuBTree](https://github.com/owensgroup/MVGpuBTree) 已支持快照及并发查询/变更 | 本轮仅原版的串行 native rank/multiset 更新 | 缺少统一 keeper/API；静态查询不能证明真正新向量插入或并发 |
| 批量更新的冗余维护 | [GrAND](https://arxiv.org/abs/2608.21163) 合并批量图修复、减少重复剪枝并处理原地删除 | U10-NATIVE 的完整操作归因；没有新机制时不做性能晋升 | 通用更新批处理已有先例；真正新机制需同契约维护成本控制 |

决定：本轮不实现新的研究机制，也不恢复“纯访存合并”或历史分配/重建收益的贡献叙事。继续用户要求的 10K 比较；只有 A0/A1 找到重要实际成本后，才按 A2 登记一个最小控制。是否存在值得研究的额外机制仍未确定。
