# 第一处大型准入失败：原生 Faiss Flat

GIST1M/960D、1024 个新开发查询、K8/B32，原生 `GpuIndexFlatL2` 在本计划的 FP64-RN oracle 下未通过完整成员及字段门槛。运行正常退出，完整原始输出和独立 audit 保留；不能把这一行称为经验100%或放入同质量精确时延比。

第531条（从0计数）、qid712558，期望末位223837，实际返回695244。独立 CPU 对全部1M对象逐维 FP64 sub/mul/add 枚举，确认 GPU reference 的前8项：kth squared =2.066523500275135，实际多出的第9项 =2.0665391422700097，差1.5641994874471266e-5，二者不是真正边界平局。

成员 Recall@8 =0.9998779296875，最差单条0.875，完整查询比例1023/1024。另一个字段失败发生在第470条 qid853005：它返回自己的距离0.008052940480411053，而真实距离为0，平方误差6.4849850381043e-5超过计划5e-5容差。字段非负且排序正常，不能用排序检查掩盖这个误差。

[Faiss 官方 FAQ](https://github.com/facebookresearch/faiss/wiki/FAQ) 说明范数展开式的有限精度抵消问题；本轮观测与这种误差一致。这里仍将其作为数值误差的解释，而不凭 FAQ 证明某个具体 GPU kernel 是唯一原因。输入、输出、CPU全枚举及原生 kernel 证据独立保存。

按停止规则，原生正式矩阵没有绕过门槛，正式10K查询也尚未生成。四个已执行的完整控制 GTS_ORIG/O_FULL/IVF_ALL/O_BOUND 在这个1024条件下通过；其他形状与原生CAGRA开发网格保持待跑，不能据此把整个比较说成完成。

## 独立的可选精算适配器

在相同开发集，单独测试 `FAISS_FLAT_REF64`：原生 Flat 搜索64个候选，GPU 显式RN-FP64逐维精算，按距离/原始ID选K，再交付全部 Euclidean FP32 字段。候选收集、精算、选择、转换、D2H和同步全计入入口计时，没有使用 oracle cutoff 或在计时后修正结果。

第一份 CuPy lexsort 调用因安装版本不接受 axis 参数失败，保留为 rejected，不作为样本。第二份使用一个固定64候选的设备选择器；GIST/K8/B32开发1024全部成员/字段通过，第一轮实测231.328ms。这个数是开发筛选，不是正式稳定性或配对优势结论。原生 Flat 的失败输出未覆盖、未改名。

有限 overfetch 的通过只说明该数据/查询集上的经验完整输出，不能保证任意FP32数据或未来所有查询100%。memcheck的32个开发查询完整输出通过，工具报告0错误；随后独立small96资格检查拒收该适配器：N4097/D96/Q48/K8/B1中13条查询成员失败，平均tie-aware Recall@8=0.7447916666666666、最差0，字段门槛通过。首个失败row19、qid128，其坐标约1e-40；CPU全部4097行确认128..135距离平方为0，但交付的是0..7，其真实距离平方约9.599896514419227e-79，并非精确边界平局。

这给出了有限候选精算不能修复所有前级漏查的实际反例。不能用字段合格或sanitizer零错误替代成员准入，也不能放宽oracle的精确边界约定掩盖反例。第二次开发、后续synccheck、尾批次和100次复用未在该拒收之后继续执行；保持pending，适配器不晋升。

参见 [REF64_FAILURE_LOCALIZATION.json](evidence/REF64_FAILURE_LOCALIZATION.json) 和 [REF64_QUALIFICATION.json](evidence/REF64_QUALIFICATION.json)。它是计划允许的传统精算对照，不提出新研究机制，也不为GTS宣称外部优势。原生Flat与可选适配器的两处失败独立保留。
