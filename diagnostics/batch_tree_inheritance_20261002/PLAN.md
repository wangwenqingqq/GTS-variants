# GTS 高维精确批量检索：P4 浅层树继承与复用保真实验计划

日期：2026-10-02
状态：**设计文档；未实现新模式，未执行本轮 GPU 实验。**
冻结起点：`wangwenqingqq/GTS-variants@43463278fa1f2b7b8e6e36ff224e5c640036963e`
建议新目录：`diagnostics/batch_tree_inheritance_20261002/`
研究定位：高维、精确、批量范围检索；单查询是兼容与诊断基础，不是研究范围上限。

## 0. 这轮只回答一个问题

**浅层树能否在已经使用布局、跨查询复用、安全早退和并行结果交付的强批量扫描上，进一步降低完整批次时间？若能，新增收益来自少做配对计算、少读共享数据，还是候选组织更高效？**

本轮不是重新搜索 batch 大小、树深、查询微块或精度格式。固定 GIST 的 C4 和查询微块 Q_T=2，以 B=8/32 为主。保留旧证据，新增结果必须与同一新二进制内重测的强扫描比较。不得把历史树收益、布局收益、输出修复收益与批量收益相乘。

## 1. 起点证据及其正确使用

已发布 P0–P3 在 GIST half、B=32 下，TILE_E 完成旧 final1024 的总 Host-ready 时间中位数约 1,784 ms；该数字不是单批延迟，更不是单查询延迟。GIST normal 的开发批次中，距离阶段约占已记录 GPU 阶段加 D2H 的 99.4%–99.6%。批量显式复用相对 GRID 已有收益，但 P4 和 cuVS 外部比较尚未执行。[R1]

这些结果决定研究顺序：先继承现有强执行器，再测树的新增价值。旧查询、硬件、计时边界以现有证据为准；下面任何尚未测量的时间、加速和阈值都不能伪装成实测事实。

## 3. 模式：四条主路径，不预设紧凑任务最好

所有路径共用AoSoA32、数值核验语义、Q_T=2、Graph策略、保序输出与有效长度D2H。`E`表示启用既有对象早退；`L`表示不早退的控制版本。

| 路径ID | 树后如何组织对象 | 是否跨查询复用同一对象值 | 用途 |
|---|---|---|---|
| `SCAN` | 不走树，原TILE扫描 | 是 | 当前强基线；首轮SCAN_E，同时保留SCAN_L |
| `C_ID` | 每查询独立稳定压缩候选位置，按候选rank处理 | 不强行共享不同ID；可在同线程维护两条查询的独立累加器并分别gather | 朴素C4批量化对照；不能退回旧pow或慢输出 |
| `C_MASK` | 保留所有原32点块，按查询掩码跳过无效对象，不压缩任务列表 | 是 | 隔离树过滤本身与候选列表压缩的成本 |
| `C_TASK` | 对查询对生成“原块ID＋两份32-bit掩码”，去掉并集为空的任务 | 是 | 候选组织与共享核验的组合方案 |

C_ID、C_MASK、C_TASK必须覆盖**完全相同的查询—对象候选集合**，并使用同样的树元数据、判定与父枢轴复用。性能差异不能由某一路径剪得更激进造成。

C_ID与C_TASK的差异包含访存、任务组织和显式共享，不把其差值全称为“纯复用收益”。C_MASK与C_TASK是本轮重要因果对照：它们保留相同掩码与对象核验规则，主要区别是是否构建和压缩任务列表。

先做全维L控制，再运行E版本，可确认候选组织作用是否依赖早退。QT=1/2在同一个C_TASK实现上的对照只在需要解释共享来源时追加，不作为新调参路线。

## 4. 共享树前缀：继承父枢轴复用，不改正确性

1. 复用历史树拓扑、pivot ID、节点成员及同一id_list，保存内容哈希。不因某模式结果不好就为它换一棵树。
2. 复用严格FP64方案的节点向外包围区间；静态refit准备单列，查询时的边界读取、区间计算与判断全部计时。沿用其有限维度与输入约定，不把测试通过称为任意输入形式化证明。
3. 对共享pivot的兄弟节点，在同一个查询上计算一次完整的查询—pivot距离区间，复用给各子节点。必须先检查实际pivot ID相同；不相同就按不同pivot分别算，不能仅凭节点名字推断共享。
4. 旧strict_walk仍作为正确性回归参考，验证新增父复用遍历产生完全相同的候选集合。主性能对照的三条树路径均用同一父复用遍历。
5. **对象E64的“部分和超过查询半径即拒绝”不能直接用于pivot距离**。pivot距离还参与壳层区间关系；首轮pivot全部算完，不增加另一种剪枝规则。
6. 将固定停止层每个逻辑位置对应的节点预计算为`node_for_pos`；运行时由真实查询遍历产生节点flag，再构造候选。不能把上一批查询的候选缓存作为本轮免费输入。

## 5. 块任务的精确定义

以两条查询q0/q1和同一个原数据块tile为单位：

- `m0`：q0在tile中需要核验的32个位置标志。
- `m1`：q1在tile中需要核验的32个位置标志。
- `m0 | m1 == 0`才可去掉整个任务。
- 并集非空就保留tile ID及两份mask，每个有效查询只计算属于自己的对象。

**禁止只留下交集。**只要一条查询需要某对象，该对象对这条查询就必须继续核验。不能因为另一条查询剪掉它，就一同丢弃。

举例（仅作机制示意）：两条查询都保留前16个对象，配对剪枝率为50%，并集保留16个对象；一条保留前16个、另一条保留后16个，配对剪枝率仍为50%，但并集覆盖全部32个对象。后者仍可能需要加载所有对象值。两种情况的DRAM流量仍需实测，不能仅从逻辑并集推断。

实现约束：

- 不复制、重打包960维向量。首轮只生成轻量任务记录；每次查询重排向量会增加混杂因素。
- 同一个(query_pair,tile)最多一条任务；多个树节点触及同一tile要合并mask。最直接的正确版本可按位置映射再ballot生成，避免重复任务。
- 一个warp处理一个32点任务，一个512线程块可处理16个任务。blockIdx.y固定所属查询微块，块内共享查询缓存与当前执行器一致。
- Graph首版采用固定上限grid，读取设备端任务数，多余warp不执行对象距离。不额外将候选数回传CPU调grid；固定上限仍可能付出多余CTA启动成本，必须如实记录，不能宣称删除了全部空块启动。
- 所有线程先完成必要的共享查询加载与块级同步，再让越界warp或线程离开。后续若有collective，所有要求参与的线程必须参与；不得发生分歧早退后的非法同步。
- 结果仍写到`flags[q*N+pos]`和`raw_distance[q*N+pos]`，交给原公共收集器，不能为新模式专门重写更快输出路径。
- 树剪掉且未调度的槽位必须为零。树路径的flags清零、node flags初始化均计时；绝不让前一批的旧hit残留。第一版三条树路径使用统一清零策略，避免把不同清零逻辑误归因为任务压缩收益。
- 最后一块不足32个对象时，尾位固定无效；地址使用size_t，批次偏移和总结果数使用64位。

## 6. 先做候选账本，分开三种“减少”

在开发查询上先运行同一严格树前缀，不需要等待C_TASK优化完成。以实际候选集合测量：

| 账本 | 统计量 | 作用 |
|---|---|---|
| 配对计算 | 进入树前/后query-object对数；每层进入/通过节点数；pivot距离次数 | 树少要求计算多少配对？ |
| 共享读取需求 | 每query-pair的候选并集、交集；非空tile数；每task有效lane数 | 两条查询同时不需要哪些对象？ |
| 早退剩余工作 | 每配对计算维度；每对象在query-pair内最长维度；每warp最长路径 | 被树排除的对象在原TILE_E中本来有多贵？ |

建议在独立计数版中定义三个互不混用的数：

- `pair_coordinate_updates`：所有实际查询—对象累加的维度数之和。
- `shared_coordinate_steps`：每对象、每query-pair中仍活动查询的最长维度之和；这是逻辑对象读取步数，不是DRAM字节。
- `warp_span_steps`：每warp任务中所有lane/查询配对的最长执行路径之和；这是尾部诊断，不是指令数或占用率。

可使用无树TILE_E独立计数得到的逐配对停止维度，与真实树mask离线交叉，估算树主要排除的是“本来很快早退的对象”还是“本来需长时间核验的对象”。该离线使用只用于诊断，不能作为线上选择器的输入，也不能据此用最终结果反向选择有利查询。

**任何只计核验、不计树遍历和task构造的回放，都必须标为kernel-only诊断，不是端到端速度。**即使账本预计优势有限，也至少保留一次未调优的真实组合试跑再决定是否扩展，不将剪枝率硬阈值当成性能定理。

## 8. 计时、配对与吞吐的精确定义

主指标`host_ready_batch_ms`：从提交已经就绪的批查询开始，到主机得到本批全部有效ID与距离。内部节点flag初始化、hit清零、树前缀、mask构建、candidate/task压缩、距离核、公共收集、count反馈、有效数据D2H、同步全部计入。

与前轮一致，预先填充pinned输入的计时边界保持不变；在契约中明确该CPU准备是否计入。不要同一张主表中有模式计入而另一些不计。

`gpu_ready_batch_ms`只作次指标：完整GPU结果已压缩生成。`QPS = 查询总数 / 各批Host-ready秒数之和`，这是该服务时间口径下的折算吞吐；正式进程中的验证hash/日志开销排除，不称为包含所有验证工作的整个进程吞吐。

- 每进程预热8个开发批次，不能拿最终查询做调参预热。
- 6轮独立进程；各模式位置轮换；同轮使用同批次成员，交替反转批次执行顺序，不改变query-pair成员。
- 记录每轮1024查询总时间、每批p50/p95描述值、摊销每查询时间与QPS。不能把T_batch/B称为请求响应延迟。
- 报同轮总时间比值、全部6轮、配对中位数、范围、按轮bootstrap区间；区间只描述这一冻结查询集上的运行波动。p95只是对应批次样本的描述，不是生产尾延迟保证。
- 计数与NSYS/NCU分开运行；新增原子计数不可混入无插桩主计时。
- 外来GPU活动、错误退出、结果失败按预先规则拒收，保留失败记录；不能仅因慢就删除一轮。固定可控的CPU/内存NUMA位置，记录而不强行变更其他用户的设置。

## 9. 必交breakdown与归因

| 阶段 | 时间字段 | 工作量字段 |
|---|---|---|
| 树前缀 | tree_walk_ms | 每层进入/通过；query-pivot次数；复用次数 |
| 候选组织 | candidate_mask_ms、task_compact_ms、clear_ms | pairs、union、intersection、非空tile、mask密度、任务记录字节 |
| 对象核验 | object_distance_ms | pair_coordinate_updates、shared_coordinate_steps、warp_span_steps |
| 输出与交付 | collect_ms、count_feedback_ms、d2h_ms | 有效结果数量、有效字节、host offsets、同步次数 |
| 整体 | host_ready_batch_ms、gpu_ready_batch_ms | 同结果hash、内存峰值、workspace与静态索引 |

NSYS测覆盖完整query流水线的范围。NCU至少分别观察树前缀、候选构造、对象核验；只报告对象核DRAM下降是不够的，必须说明新增pivot/元数据/任务读写。全流程字节与单核字节分开，不能混用不同重放范围。

涉及缓存复用时，优先选择安装版本实际支持的application/range replay，固定warmup、cache-control和clock-control策略，并保留命令。工具可能刷新缓存、重放或串行化，硬件计数不能替代主计时。[N2]

- 无树SCAN_E：距离核45 ms、其他阶段2 ms，总47 ms。
- 树方案：树和任务新增5 ms，距离核降到32 ms，其他阶段仍2 ms，总39 ms。净省8 ms。
- 若树和任务新增15 ms，总49 ms，即便距离核减少了13 ms仍是负收益。

真实结果必须使用干净Host-ready时间决定净收益。阶段时间只解释原因，不将来自另一进程的profiler阶段相加伪造端到端。

## 11. 外部强对照：本轮必须有执行记录

外部轨与内部归因轨分开：cuVS批量pairwise distance（合理支持的FP64直接L2优先，另保留官方推荐的合理优化路径）＋全部范围筛选＋保序ID/距离交付。不用top-k替代范围查询。[N1]

- 在执行者的独立环境安装/构建并固定cuVS、RAFT、CUDA及编译版本，不修改正在使用的实验环境。当前助手未安装该环境或执行远端代码。
- 最小覆盖GIST half/normal/all、B=8/32；开发阶段固定对象分块方案和库参数，不故意落地放不下的全矩阵。记录全部中间矩阵/转换与结果筛选成本。
- 输入float32转double等静态准备单列；查询数据准备、查询时转换和输出恢复原id_list顺序的成本必须记录并使用公平计时。
- C++接口包含double重载，但double不意味着累加顺序位级相同。核对完整成员集合、边界差异和距离字段，不把常规浮点次序差异自动等同于ANN漏检。[N1]
- 内部strict主表保留固定FP64序列；外部合理优化结果单列。若要纳入同一strict主表，需证明对齐路径，必要的边界回退及候选重新核验成本全计入；不可用oracle免费修复，也不可仅重算输出候选就宣称没有漏检。
- 无法安装/编译时保存准确版本、命令、错误与替代库尝试；报告“外部比较未完成”，不能据内部结果宣称领先工业实现，也不能把缺少该库作为算法胜出的证据。

## 12. 决策门槛（本轮研发规则，不是数学定理）

| 结果 | 决策 |
|---|---|
| 候选结构对最强已测匹配无树路径配对加速比≥1.10×，6轮均快，配对区间下界>1，完整输出通过 | 进入新查询/场景复验，并分析是否有独立机制贡献；尚不直接宣称论文新颖性 |
| 配对加速比1.03×–1.10×且稳定 | 保留工程组件与正向证据；不扩大成通用索引优势 |
| 配对加速比不足1.03×或轮次不稳定 | 标为未区分；停止围绕细小差异搜索深度/块大小 |
| 比C_ID快、但不如SCAN | 候选组织更好，不等于使用索引划算；分别保存两条结论 |
| C_MASK优于C_TASK | 任务压缩成本未被收回，采用MASK候选；不为维护TASK设计而挑数据 |
| 少了配对计算，但并集、shared steps或DRAM下降小 | 解释为共享读取覆盖问题，不能只展示剪枝率 |
| GPU-ready更快但Host-ready没有改善 | 不宣称完整查询收益；解释输出/控制限制 |
| 正确性失败 | 禁止进入有效性能主表；保存失败，修复后重跑 |

不因为某一场景失败就否定历史正向证据，也不因为历史有利结果就保证本轮组合一定胜出。模式开关由开发集冻结，不做事后逐查询最优选择器。
