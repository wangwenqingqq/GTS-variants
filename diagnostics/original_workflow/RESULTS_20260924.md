# 原始 GTS 更新实验：复现旧缓冲计数，验证一行修复

2026-09-24，延续固定提交 `1ab7b08` 的实验准备。原始 GTS 的更新入口确实存在一个独立于 incremental 的计数错误：缓冲区清空后，查询仍会加上上次留下的 `rnum[0]`。原版 9 个场景中 7 个通过、2 个失败；单独的 `rnum_reset` 副本只增加一行清零，9 个场景全部通过。

原始源码来自 `ZJU-DAILY/GTS@3bac1b725e92e98e3b69d5cb79ad9c56ccb5e639`，8 个文件均逐字节匹配既有哈希，实验后再次核验。仓库根目录的 incremental 文件未改动。运行使用原授权 GPU0（RTX PRO 6000 Blackwell），CUDA 13.1.115、GCC 13.3、驱动 590.48.01、Compute Sanitizer 2025.4.1。保留原生树高 3、叶容量 20、缓冲阈值 10、512 线程及 CPU 等待方式。

固定输入为 1,000 条互异的 128 维整数向量，以 FP32 存储；插入复制 row0，查询始终针对保留的 row0。每个场景独立启动。半径 0 检查重复点，半径 10,000 检查全部活动记录。独立的 CPU 活动多重集与整数平方距离生成真值。

| 场景 | 真值 | 原版实测 | 一行修复实测 |
|---|---|---|---|
| 无更新查询 | 1,1,1 | 1,1,1 | 1,1,1 |
| 全包含查询 | 1000 | 1000 | 1000 |
| 缓冲插入 | 1,2 | 1,2 | 1,2 |
| 基表删除 | 1000,999 | 1000,999 | 1000,999 |
| 查询缓冲后删除最后一条 | 2,1 | **2,2** | 2,1 |
| 未查询缓冲，直接重建 | 11 | 11 | 11 |
| 查询过缓冲，再重建并查询两次 | 2,11,11 | **2,12,12** | 2,11,11 |
| 基表删除后重建 | 1009 | 1009 | 1009 |
| 重建后删除 | 11,10 | 11,10 | 11,10 |

第一处偏离发生在 `buffer_delete` 的第 4 个操作：前面的缓冲查询留下计数 1，删除后 `in_size` 为 0，下一次查询跳过 `searchNaiveRnn`，仍把旧计数加到树结果上。重建对照也符合这一机制：没有前置缓冲查询时返回 11；留下旧计数 1 后返回 12。原版 `include/update.cuh` 在重建时清空 `in_size`，但查询只在缓冲非空时更新 `rnum`，随后无条件相加。

独立副本在可选缓冲查询前增加 `rnum[0] = 0;`，没有改变树、距离、候选集、更新阈值或分配策略。原版 8 个文件保持原样；修复副本只改动 `include/update.cuh` 的这一行。完整差异见 [rnum_reset.patch](rnum_reset.patch)，生成工具为 [repair.py](repair.py)。两个失败场景恢复正确，其余 7 个控制场景保持正确。这构成了对旧计数假设的单变量干预证据。

共保留 **47 条 GPU 运行记录**：

- 第一份原版：9 个普通场景，7 通过、2 计数失败。
- 独立复编译原版：9 个普通场景，逐项复现相同结果；该次编译返回码为 0。
- 原版两个失败场景：memcheck 均报告 0 errors，错误计数仍然存在。
- 修复副本：9 个普通场景、9 个 memcheck、9 个 synccheck，计数全部正确，18 个 sanitizer 场景均为 0 errors。

47 个被测进程均正常退出，无记录到的 CUDA 运行错误、超时或运行中外来 GPU 活动；每次运行前后均检查为空闲，并持有 `/tmp/gtspp_gpu0.lock`。计数失败没有记成通过，也没有用于性能比较。打包阶段 GPU0 已出现其他任务，因此停止 GPU 工作，仅继续读取日志。未切换 GPU、修改驱动设置或处理其他进程。

最初 SSH 编译连接在 25 秒超时，远端编译继续完成；该次编译的返回码未捕获，产物及实测仍保留。随后用 [build.py](build.py) 记录原版与修复版的完整编译命令、返回码、源码和产物哈希。两份原版二进制哈希不同，未声称二进制等价；独立编译的 9 项运行结果全部一致。第一次加锁尝试因既有锁文件的创建/追加访问权限失败，发生在 GPU 启动前；改为只读打开同一个现存锁文件并申请同样的排他锁，没有替换锁文件或绕过锁。第一次打包因末次 GPU 空闲断言失败而留下不完整包，完整证据另存新文件，没有覆盖它。

复现时先用原有 `prepare.py prepare ORIGINAL_GTS NEW_SCRATCH` 生成全新目录，再执行：

```sh
python3 diagnostics/original_workflow/repair.py "$SCRATCH"
python3 diagnostics/original_workflow/build.py "$SCRATCH" --variant original --output gts_original_verified
python3 diagnostics/original_workflow/build.py "$SCRATCH" --variant rnum_reset --output gts_rnum_reset
# GPU0 必须重新检查空闲，并通过同一锁准入；标签和输出不得覆盖旧记录。
python3 diagnostics/original_workflow/run.py "$SCRATCH" --gpu "$GPU0_UUID" \
  --label reset_buffer_delete --case buffer_delete --binary gts_rnum_reset --mode memcheck
# 分析本轮完整证据，输出目录必须不存在。
python3 diagnostics/original_workflow/analyze.py diagnostics/original_workflow/local/raw "$NEW_REPORT_DIR"
```

本轮只验证这 9 个合成整数 L2 场景的**结果数量**；没有认证完整 IDs/距离、任意数据分布、重建后的通用 ID 语义、并发更新、其他度量或持续性能。memcheck/synccheck 通过也不等于无数据竞争。本轮没有新性能对照，不能宣称加速或证明所有更新问题已解决。

后续性能实验应同时保留未修改原版和明确命名的 `rnum_reset` 正确性修复对照，再逐算子比较合并访存与 CPU/GPU 交互改动；新增工作负载先补对应真值检查。本轮代码与汇总结果由 `wangwenqingqq/GTS-variants` 的 `analysis/gts-original-update-validation-20260924` 分支承载；未合并主分支。`ZJU-DAILY/GTS` 仅为原始代码来源。
