# Small kernels and host serialization: read-only follow-up

## Analysis contract

This follow-up reuses the four accepted NSYS SQLite traces from the immutable
`gts_20260923_original_flow_words` campaign. No new GPU run, source change,
optimization, or throughput claim is introduced. Keep both full and lighter
traces, and the batched-kNN counterexample. Source hashes must still match the
original-source manifest. Original scope and profiler-overhead limitations apply.

Tests declared before the deeper extraction:

1. Count kernels below 2/5/10 microseconds, summarize duration distributions,
   and partition the repeated query into stable kernel positions.
2. Correlate host launch API intervals with GPU executions, inspect streams and
   whether the next launch starts only after the previous kernel finishes.
3. Count explicit device waits, stream waits, scalar copy-back, and allocations
   in complete init-to-next-init cycles. Map them to source dependencies.
4. Intersect recorded GPU-idle intervals with CUDA API intervals. This is
   temporal overlap, not attribution to CPU arithmetic or removable wall time.
5. Distinguish redundant host waits from mandatory host-consumed dependencies;
   do not equate a single stream with a defect or propose deleting every wait.

Results are appended below after extraction; reproducible numeric evidence is
`ASYNC_EVIDENCE.json`, generated by `analyze_async.py` from the excluded raw traces.

## Result: both fragmentation and host serialization are established here

The accepted lighter update trace contains **98,304 kernels / 4,096 queries =
24 kernels per query**. Median kernel duration is **2.112 us**; 81,685 kernels
(**83.09%**) take at most 5 us and 88,730 (**90.26%**) at most 10 us. This is
traced duration, not an unprofiled microbenchmark. The earlier analysis records
87.76% one-block launches; duration and grid size are separate observations.

Every one of the 4,095 complete init-to-next-init cycles has the same counts:

| Operation | Per cycle | Explanation |
|---|---:|---|
| GPU kernels / host launches | 24 | 12 application kernels + 12 library scan/reduce kernels |
| `cudaDeviceSynchronize` | 12 | Explicit application waits |
| `cudaStreamSynchronize` | 9 | Five scans plus two waits around each of two host-returning reductions |
| `cudaMemcpyAsync` | 2 | Two 4-byte D2H scalar results; both immediately followed by stream sync |
| `cudaMalloc` | 16 | Nine application allocations + seven observed library workspaces |
| `cudaMallocManaged` | 8 | Application allocations |
| `cudaFree` | 24 | Application and temporary library allocations released again |

The cycle begins at one `initQnode` launch API and ends before the next. It
includes the current query's cleanup and next query's initial allocation, so it
is not a separately instrumented source-function range. The final incomplete
cycle is omitted. All 4,096 complete GPU query patterns have identical 24 names.
The heavier trace independently reproduces these counts.

All query kernels are on the same recorded stream, with no kernel overlap.
**85,556 / 98,303 (87.03%)** adjacent kernel pairs have the next host launch API
start only after the previous GPU kernel has ended. This is a submission-timing
proxy, not a hardware queue-depth metric. A single stream can still queue work
asynchronously; the problem is repeated host waits and feedback, not merely the
absence of multiple streams.

## The repeated flow and exact source boundaries

Source is unchanged author commit `3bac1b725e92e98e3b69d5cb79ad9c56ccb5e639`;
all eight CUDA files were rehashed against the original manifest. Locations below
are in `GTS/include/update.cuh`, unless explicitly noted otherwise.

```text
CPU sets one query ID
  -> init query flags -> device wait
  -> [traverse one level -> wait -> update flags -> wait] x 2
  -> reduce candidate count -> D2H 4 B -> wait -> allocate by that count
  -> init / count / scan / compact candidate leaves
  -> leaf distance computation -> wait
  -> reduce result count -> D2H 4 B -> wait -> allocate by that count
  -> count / scan / compact results -> wait
  -> CPU reads result count -> allocate final result
  -> scan deletion flags -> merge -> wait
  -> print + flush -> free -> next query
```

- `GTS/src/main.cu:150` fixes `qnum=1` for the update entry. The operation loop
  is `update.cuh:473`; host query-ID assignment is line 588. Batched kNN does
  not use this one-at-a-time launch schedule.
- Lines **352-370, 392-416, 425-432** repeatedly launch and immediately wait.
  For example, the producer `findNextRnn` and consumer `updatePnodeFlag` use the
  same implicit stream, but the host waits between them instead of simply
  queuing the ordered dependency.
- Lines **384-391** return `search_num` to the host to size five buffers. Lines
  **421-424** return `result_num` to size two more. These are actual control
  dependencies in the current allocator design, not waits that can be blindly
  deleted. All 8,192 observed async-copy calls are immediately followed by a
  stream wait and correspond to 4-byte D2H transfers.
- Lines **404-406, 428-429, 601** invoke five synchronous-policy Thrust scans.
  Each produces `DeviceScanInitKernel` plus `DeviceScanKernel`. Two additional
  host-returning reductions give 12 of the 24 launches and seven temporary
  allocation/free pairs per query.
- Lines **597-617** add a host read of managed result count, final allocation,
  merge, synchronization, per-query `fprintf`/`fflush`, and cleanup. UVM handling
  and logging may contribute to unassigned host intervals; this trace does not
  causally separate them.

CUDA launches are normally asynchronous with respect to the host; the original
program immediately waits after many of them. Also, an `Async` suffix alone does
not guarantee host-nonblocking behavior. See the version-matched
[CUDA 13.1.1 synchronization documentation](https://docs.nvidia.com/cuda/archive/13.1.1/cuda-runtime-api/api-sync-behavior.html).
The default CUDA Thrust policy synchronizes before returning; `par_nosync` is
only a hint and cannot remove a wait required to return a host scalar. This is
explained in NVIDIA's [Thrust stream-policy example](https://github.com/NVIDIA/thrust/blob/main/examples/cuda/explicit_cuda_stream.cu).
These semantics explain the observed sequence; they are not an A/B speedup claim.

## Where the GPU-idle intervals coincide with host calls

Of the lighter trace's **2,096.418 ms** without recorded GPU work:

| Concurrent host-side interval | Intersection with GPU gaps (ms) |
|---|---:|
| Allocation/free API | 734.380 |
| Kernel launch API | 374.212 |
| Device/stream synchronization API | 370.080 |
| Copy API | 76.011 |
| Outside these recorded CUDA API intervals | 541.736 |

These intersections are computed as disjoint interval unions, not summed raw
API durations. In particular, the earlier 1,082.497-ms inclusive sync-API sum
contains GPU execution time; it is **not** 1,082.497 ms of removable overhead.
Likewise, GPU-idle time overlapping synchronization does not prove CPU spinning.
All values include tracing effects. The heavier trace leaves much more time
outside CUDA APIs, reinforcing that gaps cannot be equated to useful CPU work.

## Prioritized changes to test, not implemented or promoted

1. **Queue same-stream dependencies without intermediate host waits.** A
   conservative first control can target the ten explicit waits per query at
   lines 353, 364 (twice), 370 (twice), 393, 400, 409, 416 and 427. They sit
   between ordered device operations rather than an immediate host consumption
   of their results. Keep completion before host consumption / buffer reuse,
   preserve asynchronous-error reporting, and recheck managed-memory access and
   sanitizers. This is a static candidate list, not ten proven removable costs.
2. **Reuse workspace; remove host-sized allocation feedback where possible.**
   Reserve bounded storage outside the per-query loop and retain device counts.
   Simply renaming calls to `Async` or adding streams does not break the scalar
   result -> host allocation dependency. Measure allocation reuse independently
   before combining it with synchronization changes.
3. **Eliminate trivial/repeated scan work, then consider fusion or batching.**
   In this qnum=1 path, the two exclusive scans of per-query counts each have
   length one, so their output is zero; four launches per query implement these
   two trivial prefixes. The deletion flags never change in this query-only
   workload, yet their full prefix scan is recomputed at line 601 each query.
   Maintain/invalidate that prefix on actual updates rather than claiming it
   can be skipped for arbitrary mixed operations. Fuse initializations with a
   safe producer, not with a consumer requiring a grid-wide barrier. Batch only
   independent queries without violating intervening update visibility.

Adding streams also requires ownership changes: `search.cuh:13-33` keeps query
workspace pointers in globals, and `update.cuh:588` overwrites one shared query
ID. Concurrent queries need separate in-flight state, not just different streams.

Do not attribute everything to tiny launches: `getQresultCount` has a traced
median of **47.136 us**, versus **34.144 us** for `leafProcessRnnUpdate`.
`GTS/include/search.cuh:574-585` assigns one query to an output-owning thread and
calls a device-side Thrust reduction. This deserves separate generated-code and
counter analysis; the current trace is not proof of its exact internal execution
strategy, nor a reason to remove it before preserving the output contract.

## Counterevidence and scope

Batched kNN has **27 kernels for all 4,096 queries**, median kernel duration
56.863 us, and 70.4% GPU-work coverage in the lighter trace. It also uses a single
stream and contains synchronization, but does not suffer the same per-query
24-launch amplification. Therefore neither single-stream use nor a raw sync count
alone is a sufficient bottleneck diagnosis.

This remains Words N=2,000, repeated checked queries, no insertions/deletions.
NCU was unavailable to the initial non-elevated calls; a later
[privileged follow-up](NCU_PRIVILEGE_RETRY.md) successfully collected counters.
This async audit itself introduced no GPU job or optimized executable;
no speedup, whole-host CPU saturation, full-dataset result, or universal GPU-tree
claim is established by this follow-up.
